# V3.3 Output Contract

This describes the current implementation in `sleeper_v3_2.py`; it is a reference to the existing output, not a proposed schema. Examples are abbreviated JSON fragments with synthetic IDs. `...` means other entries/fields are omitted. Python lists and dictionaries serialize as JSON arrays and objects.

## Compatibility and intended use

- **Existing V3.2-compatible fields:** the snapshot envelope, `snapshot_version`, `fantasy_analysis.lineup_requirements`, `flex_positions`, `teams`, `position_summary`, `position_need`, `starting_depth`, `optimal_lineup`, `lineup_strength`, `roster_surplus`, `roster_replacement_cost`, `player_protection`, `league_position_analysis`, `league_position_scarcity`, and waiver-analysis fields retain their names and general types. Some values now derive from configured slots.
- **V3.3 configuration-aware additions:** normalized `roster_configuration`, `flex_slot_requirements`, `configuration_demand`, per-FLEX-type coverage, coverage assignments/summary, and optimizer keys for configured FLEX types other than `FLEX`.
- **Compatibility fields:** `snapshot_version` intentionally remains `"3.2"`; aggregate `lineup_requirements["FLEX"]` and `lineup_coverage["FLEX"]` remain even when several FLEX types exist. They do not replace per-type detail.
- **UI-oriented analysis:** `position_need`, `starting_depth`, `lineup_strength`, `roster_surplus`, `roster_replacement_cost`, `player_protection`, and waiver candidates are decision-support outputs. Configuration, player records, position summaries, league aggregation, coverage counts, and slot assignments are also available as data/information. No field is an HTTP API guarantee.

## Snapshot envelope assembled in `main()`

`main()` creates a snapshot with these top-level keys. Its comparison value is populated after initial construction.

```json
{
  "snapshot_timestamp": "2026-10-02 12:00:00",
  "snapshot_version": "3.2",
  "league": {
    "league_id": "league-demo",
    "name": "Example League",
    "season": "2026",
    "status": "in_season",
    "settings": {},
    "roster_positions": ["QB", "RB", "RB", "WR", "WR", "TE", "FLEX", "K", "DEF"],
    "scoring_settings": {}
  },
  "season": "2026",
  "week": 5,
  "nfl_state": {},
  "users": {},
  "rosters": {},
  "waiver_order": [],
  "waiver_pool": [],
  "transactions": [],
  "matchups": {},
  "standings": [],
  "comparison": {},
  "fantasy_analysis": {},
  "waiver_analysis": {}
}
```

The `users`, `rosters`, `nfl_state`, `matchups`, `standings`, and `comparison` contents come from other existing snapshot builders and Sleeper data; this document does not redefine those contracts. `league.roster_positions` is the raw Sleeper array. The normalized configuration appears under `fantasy_analysis.roster_configuration`.

## Normalized roster configuration

`parse_roster_configuration()` returns a JSON-friendly object:

```json
{
  "direct_slots": {"DEF": 1, "K": 1, "QB": 1, "RB": 2, "TE": 1, "WR": 2},
  "flex_slots": {"FLEX": {"count": 1, "eligible_positions": ["RB", "WR", "TE"]}},
  "nonstarter_slots": {"BN": 6},
  "unrecognized_slots": {}
}
```

The direct map counts repeated direct slots. Each FLEX entry has integer `count` and array `eligible_positions`. `BN` is nonstarter capacity. Unrecognized codes remain in `unrecognized_slots` and are not converted into supported analyzer positions. Recognized direct codes include QB/RB/WR/TE/K/DEF/DL/LB/DB. FLEX eligibility is `FLEX` → RB/WR/TE, `WRRB_FLEX` → RB/WR, `REC_FLEX` → WR/TE, `SUPER_FLEX` → QB/RB/WR/TE, and `IDP_FLEX` → DL/LB/DB.

The internal `expand_roster_slots()` representation is an array of instances with `slot_code`, one-based `ordinal`, `eligible_positions`, `slot_type`, `is_direct`, `is_flex`, `recognized`, and `supported_by_analyzer`. It is deterministic. Direct K/DEF slots are supported for coverage; DL/LB/DB and IDP_FLEX are preserved but are not supported by the current player analyzer.

## `fantasy_analysis`

The top-level keys returned by `build_fantasy_analysis()` are:

```json
{
  "roster_configuration": {},
  "lineup_requirements": {"QB": 1, "RB": 2, "WR": 2, "TE": 1, "K": 1, "DEF": 1, "FLEX": 1},
  "flex_positions": ["RB", "TE", "WR"],
  "flex_slot_requirements": {"FLEX": {"count": 1, "eligible_positions": ["RB", "WR", "TE"]}},
  "teams": {"roster-demo": {}},
  "league_position_analysis": {},
  "league_position_scarcity": {}
}
```

`lineup_requirements` counts configured direct positions and retains an aggregate `FLEX` count across configured FLEX types. `flex_positions` is the sorted union of configured FLEX eligibility; it does not mean each listed position has its own separate FLEX slot. `flex_slot_requirements` preserves each type and its eligibility.

### Per-team structure

Each `teams` value is keyed by string roster ID and contains:

```json
{
  "team_name": "Synthetic Team",
  "owner": "Synthetic Owner",
  "positions": {"QB": [], "RB": [], "WR": [], "TE": [], "K": [], "DEF": []},
  "position_summary": {},
  "lineup_coverage": {},
  "position_need": {},
  "optimal_lineup": {},
  "starting_depth": {},
  "lineup_strength": {},
  "roster_surplus": [],
  "roster_replacement_cost": [],
  "player_protection": []
}
```

`positions` is grouped by QB/RB/WR/TE/K/DEF. A player record has `player_id`, `name`, `team`, `status`, `injury_status`, `roster_status`, `fantasy_value_tier`, and integer `importance_score`. `roster_status` is one of starter/bench/reserve/taxi. `position_summary` has one record per analyzed position with integer `total`, `starters`, `bench`, `reserve`, `taxi`, `depth_score`, and `meaningful_players`. Here `starters` means Sleeper roster starter membership; it is not the optimizer’s computed lineup count.

### Optimal lineup

The optimizer returns an object from slot-code keys to arrays of player records. It always initializes QB/RB/WR/TE/FLEX arrays; configured supported FLEX types such as `WRRB_FLEX` get their own key. The arrays contain selected players only, so an underfilled slot appears as a shorter array, not a placeholder.

```json
{
  "QB": [{"player_id": "player-q1", "position": "QB", "fantasy_value_tier": "elite", "importance_score": 7}],
  "RB": [{"player_id": "player-r1", "position": "RB"}, {"player_id": "player-r2", "position": "RB"}],
  "WR": [{"player_id": "player-w1", "position": "WR"}, {"player_id": "player-w2", "position": "WR"}],
  "TE": [{"player_id": "player-t1", "position": "TE"}],
  "FLEX": [{"player_id": "player-w3", "position": "WR"}]
}
```

Selections are globally optimized across supported configured offensive slots, with unique player use. The optimizer supports QB/RB/WR/TE only. K/DEF are not selected; IDP is not implemented.

### Lineup coverage

Direct position entries contain `required`, `total`, `direct_coverage`, `surplus`, and `shortage`. K/DEF direct coverage is represented separately from offensive FLEX assignment. The aggregate `FLEX` key is retained for compatibility and contains `required`, `supported_required`, `eligible_players`, `coverage`, `shortage`, and `unsupported`. Its eligible-player count is a unique-player union across configured FLEX types; it is not a count of assignable slots.

`flex_slots` reports those same slot-level counts separately by actual FLEX code. `summary.assignments` lists only filled supported slots:

```json
{
  "FLEX": {"required": 2, "supported_required": 2, "eligible_players": 4, "coverage": 2, "shortage": 0, "unsupported": 0},
  "flex_slots": {
    "FLEX": {"required": 1, "supported_required": 1, "eligible_players": 3, "coverage": 1, "shortage": 0, "unsupported": 0},
    "REC_FLEX": {"required": 1, "supported_required": 1, "eligible_players": 2, "coverage": 1, "shortage": 0, "unsupported": 0}
  },
  "summary": {
    "supported_configured_slots": 10,
    "covered_slots": 9,
    "uncovered_slots": 1,
    "unsupported_slots": {},
    "assignments": [{"slot_code": "REC_FLEX", "ordinal": 1, "slot_type": "flex", "player_id": "player-w3", "position": "WR"}]
  }
}
```

Each direct assignment has `slot_code`, `ordinal`, `slot_type`, `player_id`, and `position`. One player can cover at most one assignment. FLEX coverage excludes inactive, IR, and non-meaningful players. The direct-slot assignment path does not apply those FLEX-only filters.

### Position need and starting depth

For QB/RB/WR/TE, `position_need` values include `need` and `reason`; when comparative inputs are available, they also include `depth_difference` and `meaningful_difference`. `need` is high/moderate/low, or unknown when league comparison is unavailable. Direct configured demand drives actual starter-shortage checks; shared FLEX slots are not independently added to each position’s demand.

`starting_depth` values contain integer `required`, `starters`, `direct_shortage`, `direct_surplus`, `meaningful_players`, `flex_available`, and a `starting_depth` label. Labels follow the existing position-specific logic (for example short/thin/deep, with `covered_by_flex` for applicable RB/WR shortage cases). `flex_available` counts assigned optimized flex players of that position, not every theoretically eligible roster player.

```json
{
  "position_need": {"RB": {"need": "moderate", "reason": "RB depth is below the league median."}},
  "starting_depth": {"RB": {"required": 2, "starters": 2, "direct_shortage": 0, "direct_surplus": 0, "meaningful_players": 3, "flex_available": 1, "starting_depth": "deep"}}
}
```

### Lineup strength

`lineup_strength` maps QB/RB/WR/TE to `rating`, `meaningful_players`, `direct_shortage`, and `flex_used`. It evaluates the optimizer’s unique configured lineup assignments while retaining the established position-specific strength labels and thresholds.

```json
{"RB": {"rating": "adequate", "meaningful_players": 3, "direct_shortage": 0, "flex_used": 1}}
```

### Roster surplus

`roster_surplus` is an array for meaningful offensive players only: tiers elite/strong/useful. Each record contains `player_id`, `name`, `position`, `fantasy_value_tier`, `roster_status`, `in_optimal_lineup`, and `surplus_type` (`needed`, `replaceable`, or `surplus`). Here `roster_status` is reduced to `injured` for IR, `starter` for starters, and `bench` otherwise (including reserve/taxi players). Slot coverage uses unique player assignments. This is not an all-roster-player listing.

```json
[{"player_id": "player-r3", "name": "Synthetic RB", "position": "RB", "fantasy_value_tier": "useful", "roster_status": "bench", "in_optimal_lineup": false, "surplus_type": "surplus"}]
```

### Replacement cost and player protection

`roster_replacement_cost` is an array for each unique QB/RB/WR/TE roster player with a non-null ID, including players outside meaningful tiers. It compares the best legal optimizer score before and after removing that player. A non-contributing bench player may have zero cost. Fields are:

`player_id`, `name`, `position`, nullable `lineup_position`, nullable `replacement_player`, nullable `replacement_player_id`, nullable `replacement_lineup_position`, nullable `replacement_tier`, integer `lineup_score_before`, integer `lineup_score_after`, integer `score_difference`, and `replacement_cost` (`very_high`, `high`, `moderate`, `low`). K/DEF are outside this calculation.

```json
[{"player_id": "player-r1", "name": "Synthetic RB", "position": "RB", "lineup_position": "RB", "replacement_player": "Backup RB", "replacement_player_id": "player-r3", "replacement_lineup_position": "RB", "replacement_tier": "useful", "lineup_score_before": 500, "lineup_score_after": 300, "score_difference": 200, "replacement_cost": "high"}]
```

`player_protection` is derived from surplus and replacement-cost rows. Its records contain `player_id`, `name`, `position`, `fantasy_value_tier`, nullable `replacement_cost`, nullable `replacement_player`, nullable `score_difference`, `protection`, and `reason`.

```json
[{"player_id": "player-r1", "name": "Synthetic RB", "position": "RB", "fantasy_value_tier": "elite", "replacement_cost": "high", "replacement_player": "Backup RB", "score_difference": 200, "protection": "protect", "reason": "Elite fantasy asset."}]
```

### League position analysis and scarcity

`league_position_analysis` contains `configuration_demand`, entries for QB/RB/WR/TE/K/DEF, and a compatibility `FLEX` aggregate when FLEX slots exist.

`configuration_demand` has `direct_demand_by_position`, `flex_demand_by_slot_code`, `eligible_flex_slot_instances_by_position`, `total_configured_starting_slots`, `supported_starting_slots`, `unsupported_slot_counts`, and `by_roster`. Shared eligibility counts overlap across positions; they are not independent direct requirements. Each `by_roster` entry contains `direct_slots`, `flex_slots`, `configured_starting_slots`, `supported_starting_slots`, and `unsupported_slots`.

Each positional league entry retains a `teams` array (`roster_id`, `team_name`, `total`, `starters`, `bench`, `depth_score`, `meaningful_players`) and the aggregate fields `configured_direct_demand`, `eligible_flex_slot_instances`, `average_total`, `median_total`, `minimum_total`, `maximum_total`, `average_depth_score`, `median_depth_score`, `minimum_depth_score`, `maximum_depth_score`, `average_meaningful_players`, `median_meaningful_players`, `minimum_meaningful_players`, and `maximum_meaningful_players`.

The `FLEX` aggregate contains `teams` (each with `roster_id`, `team_name`, `meaningful_flex_players`, and `configured_flex_slots`), `configured_slots`, `slot_counts_by_type`, `eligible_positions_by_type`, and average/median/minimum/maximum meaningful FLEX player counts. This FLEX supply is an informational heuristic after direct-player exclusion; it is not another optimizer result.

`league_position_scarcity` maps QB/RB/WR/TE to `scarcity`, `median_depth_score`, `average_depth_score`, and `average_meaningful_players`. Thresholds are unchanged: High if median depth ≤8 or average meaningful ≤1.5; Moderate if median depth ≤14 or average meaningful ≤2.5; otherwise Low.

```json
{
  "league_position_analysis": {
    "configuration_demand": {
      "direct_demand_by_position": {"QB": 12, "RB": 24, "WR": 24, "TE": 12, "K": 12, "DEF": 12},
      "flex_demand_by_slot_code": {"FLEX": {"count": 12, "eligible_positions": ["RB", "WR", "TE"]}},
      "eligible_flex_slot_instances_by_position": {"QB": 0, "RB": 12, "WR": 12, "TE": 12, "K": 0, "DEF": 0},
      "total_configured_starting_slots": 108,
      "supported_starting_slots": 108,
      "unsupported_slot_counts": {},
      "by_roster": {"roster-demo": {"direct_slots": {"QB": 1, "RB": 2, "WR": 2, "TE": 1, "K": 1, "DEF": 1}, "flex_slots": {"FLEX": {"count": 1, "eligible_positions": ["RB", "WR", "TE"]}}, "configured_starting_slots": 9, "supported_starting_slots": 9, "unsupported_slots": {}}}
    },
    "RB": {"configured_direct_demand": 24, "eligible_flex_slot_instances": 12, "average_total": 5.0, "median_depth_score": 16, "average_meaningful_players": 2.4},
    "FLEX": {"configured_slots": 12, "slot_counts_by_type": {"FLEX": 12}, "eligible_positions_by_type": {"FLEX": ["RB", "WR", "TE"]}, "average_meaningful_players": 2.0}
  },
  "league_position_scarcity": {
    "RB": {"scarcity": "moderate", "median_depth_score": 16, "average_depth_score": 16.5, "average_meaningful_players": 2.4}
  }
}
```

## Waiver analysis

`waiver_analysis` is a sibling of `fantasy_analysis` at the snapshot root. If the configured target team is absent, the result is `{"available": false, "candidates": []}`. Otherwise it contains `available: true`, the team name, and candidate records with `player_id`, `name`, `position`, `team`, `status`, `injury_status`, `search_rank`, `team_need`, `league_scarcity`, and integer `waiver_value_score`.

```json
{
  "available": true,
  "team": "Synthetic Team",
  "candidates": [{"player_id": "waiver-w1", "name": "Synthetic WR", "position": "WR", "team": "SYN", "status": null, "injury_status": null, "search_rank": 90, "team_need": "moderate", "league_scarcity": "high", "waiver_value_score": 70}]
}
```

Only QB/RB/WR/TE waiver candidates are analyzed. The score combines the existing search-rank points with configuration-aware team need and league scarcity. K/DEF/IDP are not currently included.
